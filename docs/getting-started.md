# Run Team Agent with your own team

This guide takes you from a source checkout to a real task executed by a teammate's local Codex, tested, and pushed to your project's shared working branch.

It describes the current `main` source. The published **v0.2.0 release archives and container images are older** and do not contain the verified-goal workflow. Build the Coordinator and every Runner from the current source for this guide. Updating GitHub Pages does not update an installed Runner or publish a new container image.

The [public demo](https://boxzeemon-beep.github.io/team-agent/) runs a simulation in your browser. It cannot connect your account, run Codex, or change a Git repository. Use your own Coordinator URL for the steps below.

Follow the numbered steps for a first installation, or jump to the operation you need:

- [Prerequisites and local Codex/Git access](#prerequisites)

## What runs where

| Component | Who runs it | What it needs |
| --- | --- | --- |
| Coordinator | One team administrator, on a machine the team can reach | Node.js 22.13+ and pnpm 11 for a source installation, or Docker with Compose; persistent storage |
| Runner | Each person who shares an Agent, on their own computer | Current Team Agent source, Node.js 22.13+, pnpm 11, Git, a working local Codex CLI login, and the project's development tools |
| Browser | Every member who requests or reviews work | A personal invitation and network access to the Coordinator |

A browser-only member does not need a local Codex installation. The Runner uses its owner's Codex access and Git credentials. Those credentials stay on that computer; task conversations, progress, diffs, test output, and results are sent to the Coordinator.

There is **one project and one active code task per Coordinator**. Members explicitly choose an Agent. Several Agents can be connected, but this version does not write to the project in parallel or create a separate pull request for every task.

## 1. Prepare the Coordinator and Runner machines

Install Node.js 22.13 or later; the latest Node.js 22 or 24 release is a suitable choice. On source installations, install the package-manager version specified by this repository:

```sh
node --version
npm install --global pnpm@11.9.0
pnpm --version
git --version
```

If your machine already manages pnpm through Corepack or another package manager, use that installation instead of installing a second copy. The repository's `packageManager` field is the version to follow when updating.

Use PowerShell 7+ on Windows for the commands generated by the web UI. On macOS or Linux, use bash or zsh. If you choose WSL, install Node, Git, Codex, and the Runner inside the same WSL environment and perform the checks there; a login in a different environment is not a substitute.

### Install and sign in to Codex on each Runner machine

Follow the [official OpenAI Codex CLI installation guide](https://learn.chatgpt.com/docs/codex/cli). Its npm installation option works with the Node installation used here:

```sh
npm install --global @openai/codex
codex --version
codex login
codex login status
```

Complete the browser sign-in on that Runner owner's account. OpenAI also documents other authentication methods and headless-device options in its [authentication guide](https://learn.chatgpt.com/docs/auth). Native Windows users should complete any required [Windows sandbox setup](https://learn.chatgpt.com/docs/windows/windows-sandbox) before sharing their Agent.

The Team Agent Runner starts `codex app-server` itself. Do not start a second app-server for it. `codex` must be available on the Runner process's `PATH`; if needed, `CODEX_BIN` can point to the actual Codex executable. The Coordinator does not need a Codex login.

### Verify access to your project repository

Use a repository your team is authorized to modify. Each Runner owner needs Git transport access to clone/fetch it and push to the chosen shared branch. A GitHub browser session or connector connection does not, by itself, configure terminal Git authentication.

From an ordinary checkout of **your project**, run:

```sh
git remote -v
git ls-remote origin HEAD
git push --dry-run origin HEAD:refs/heads/codex/team-agent-access-check
```

The last command does not create the remote branch. If authentication is required, finish the Git credential-manager or SSH setup on this machine, then repeat the check. Use the same operating-system account that will run the Runner. A dry-run verifies the transport path; server-side branch rules may still reject a later real push.

For a first deployment, use a dedicated working branch such as `codex/team-agent-runtime`, with an explicit path for its owners to push. Review and merge that branch into your protected base branch through your normal process. Do not choose `main` as the shared working branch unless direct pushes to `main` are deliberately part of your team's workflow.

## 2. Build the current source

On the Coordinator host, and separately on every Runner host:

```sh
git clone https://github.com/boxzeemon-beep/team-agent.git
cd team-agent
pnpm install --frozen-lockfile
pnpm build
```

This builds both the web app/Coordinator and the Runner. The resulting commands are:

```sh
node apps/coordinator/dist/server/index.js
node apps/runner/dist/cli.js --help
```

Run them from the Team Agent source checkout, not from the project you want the Agent to edit. The Runner creates its own managed clone of that project.

Keep the Coordinator and Runners on the same source revision when possible. The package version may still read `0.2.0`; verified-goal support is identified by the Runner's `goal-workflow-v1` capability, not that version label alone.

## 3. Choose your team's URL and start the Coordinator

**Choose the URL members will actually use before claiming the first administrator invitation.** For one-machine evaluation, use `http://127.0.0.1:4310`. For teammates on other machines, first follow [network deployment](#network-deployment) and use the final LAN or HTTPS URL. `127.0.0.1` on a teammate's computer points to that teammate's own computer.

Create a local environment file. On macOS/Linux:

```sh
cp .env.example .env
```

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

For evaluation on this computer, the relevant values are:

```dotenv
TEAM_AGENT_HOST=127.0.0.1
TEAM_AGENT_PORT=4310
TEAM_AGENT_PUBLIC_URL=http://127.0.0.1:4310
TEAM_AGENT_DATA_DIR=.data/coordinator
TEAM_AGENT_LOG_LEVEL=info
TEAM_AGENT_DEMO_MODE=0
```

Start the built application with the environment file explicitly loaded:

```sh
node --env-file=.env apps/coordinator/dist/server/index.js
```

Keep this terminal open. The built-in Node `--env-file` option is intentional: running `pnpm coordinator:built` by itself does not load `.env`. Variables already set in the process environment take precedence over the file, so remove an old `TEAM_AGENT_DEMO_MODE=1` or conflicting deployment setting from your shell if necessary.

Open `http://127.0.0.1:4310/api/health` for the local example. A working server responds with JSON containing `"service":"team-agent-coordinator"` and `"status":"ok"`. The app UI is served on the same port.

### Claim the administrator invitation

On a database with no members, the Coordinator prints:

```text
Bootstrap admin invite: https://YOUR_COORDINATOR/invite?token=...
```

Open the complete URL in your browser, enter your name, and select **Join workspace**. The first member is the administrator. The invitation is single-use and expires after seven days. Restarting an unclaimed, empty installation issues a new administrator link and retires the previous unused link; use the latest log entry.

Save this browser session. Team Agent currently uses invitation-based browser sessions; it does not provide a password login, a sign-in email, or a self-service account-recovery screen. Restarting a Coordinator that already has members does **not** generate another administrator invite. Switching browser profiles, clearing cookies, or moving to a different hostname can leave you without access to the existing administrator identity.

Do not publish administrator links or pairing tokens in screenshots, logs shared with the team, or public issues.

## 4. Configure the project

In the web app, open **Project settings** using the project name at the top or the settings control. The administrator can edit:

| Field | Example | Meaning |
| --- | --- | --- |
| Project name | `My product` | Name shown to members |
| Git repository URL | `https://github.com/YOUR_ORG/YOUR_PROJECT.git` | The exact clone URL every Runner can access; an SSH clone URL is also possible |
| Base branch | `main` | Existing remote branch used when the shared branch does not yet exist |
| Shared working branch | `codex/team-agent-runtime` | Branch the Runner updates and pushes |
| Test command | `pnpm install --frozen-lockfile && pnpm test` | A real command run from the root of the managed project clone |

Click **Save project settings**. These examples are placeholders: use your own repository, branch names, package manager, and verification command.

The repository must already contain at least one commit and the configured base branch. If the shared branch already exists remotely, the Runner starts from it. Otherwise it starts from `origin/<base branch>` and creates/pushes the shared branch when a task completes.

### Prepare a test command that works in a fresh clone

The Runner does not copy your everyday checkout, install dependencies automatically, or copy untracked `.env` files. It creates a managed clone under its data directory. Install the project's language runtimes and required tools on every Runner host, and configure the environment needed by its tests.

For example, a Node project might use `npm ci && npm test`, or the pnpm command above. A Python project whose environment is already prepared might use `python -m pytest`. These are examples, not commands that Team Agent automatically chooses.

The configured command must terminate: do not use a watch-mode test process or a development server. It runs in the Runner owner's shell with that process's permissions and environment. Only configure commands and repositories you trust to run on that computer.

A verified goal requires a nonempty test command and a successful result. A direct task permits an empty command, but its result then has no test verification. Configure a real check even for your first direct task when your project supports one.

Project settings are captured when a task is assigned. Changing them while a task is running does not retarget that active execution.

## 5. Invite teammates

In **Project settings**, use **Create invite**, then **Copy invite link**. Send one new invitation to each teammate through your usual private channel.

Each link is single-use and expires after seven days. A teammate opens it in the browser/profile they intend to keep using, enters their name, and selects **Join workspace**. These invitations create ordinary members, not additional administrators. Browser-only members can request work and inspect results without installing the Runner.

A new invitation creates a new member identity; it is not a password-reset link for an existing member. Agent ownership belongs to the member who generated that Agent's pairing command.

## 6. Pair each owner's local Runner

The Agent owner should sign into their own Team Agent member session before pairing.

1. On that owner's computer, finish the Codex and Git checks from step 1 and build the current Team Agent source.
2. In the web app, select **Connect Agent**, choose a recognizable name, and select **Generate pairing command**.
3. Choose the matching terminal: **Windows (PowerShell 7+)** or **macOS / Linux (bash, zsh)**.
4. Select **Copy pairing command** and run it from the Team Agent checkout on that owner's computer.

The current-source command has this form:

```sh
node apps/runner/dist/cli.js runner --coordinator 'https://team.example.com' --pair 'PAIRING_TOKEN' --name 'Alex Codex'
```

Replace the placeholders with the generated values. Prefer the generated command for names containing apostrophes or other shell-sensitive characters; the UI supplies the appropriate literal quoting for each shell.

The pairing token expires after 15 minutes and can register one device. If it expires before the first connection, generate a new command. A successful start prints messages such as `Codex: signed in and ready`, `Agent: online`, and `Agent: ready for team tasks`. Your Agent then appears in the web app.

### Check readiness without starting a task

From the same checkout and operating-system user:

```sh
node apps/runner/dist/cli.js doctor --coordinator 'https://team.example.com'
```

Doctor checks the Node version, Coordinator health, Git executable, Codex login/app-server handshake, and Runner data-directory access. It does not run a model task or prove that Git push authentication and your project's tests work; verify those separately.

### Restart the same Agent later

Stop the Runner with Ctrl+C. To reconnect the same device, use the same Coordinator URL and data directory **without the one-time pairing token**:

```sh
node apps/runner/dist/cli.js runner --coordinator 'https://team.example.com' --name 'Alex Codex'
```

By default, the Runner stores its device token, checkpoints, completion receipts, and managed clones in:

- macOS/Linux: `~/.team-agent/runner/`
- Windows: `%USERPROFILE%\.team-agent\runner\`

For a dedicated location, add `--data-dir '/absolute/path/to/my-project-runner'` on macOS/Linux or `--data-dir 'C:\TeamAgentData\my-project-runner'` on Windows. Reuse that exact directory for pairing, normal restarts, doctor, and recovery commands. Use a different directory for a different Coordinator or device identity. Do not run two Runner processes against one data directory or copy its device identity to two simultaneously active machines.

Do not add a new `--pair` token to a previously paired data directory to switch identities: its stored Runner token is reused. Plan a new identity with a separate directory instead, preserving any unfinished work first.

### Keep the owner's computer available

An Agent is available only while its Runner process is running and connected. Keep the computer awake, retain network access to both the Coordinator and Codex/Git services, and leave an interactive terminal available for approvals. Closing the Team Agent browser does not stop a Runner; closing its terminal or suspending the computer can interrupt it.

Owners can use **Pause sharing** while idle and **Resume sharing** when ready. Pause is not an interrupt button for a running code task. The Coordinator may take about a minute to detect a silent network loss through its heartbeat timeout.

## 7. Run your first direct task

Choose a small, reversible change in a repository you can inspect. For example:

```text
Add docs/team-agent-onboarding.md with a short description of this repository's
existing setup and test commands. Derive the commands from the repository.
Do not change application code or tests. Summarize what you checked.
```

In the workbench:

1. Choose **Direct task**.
2. Enter the request and explicitly select an online Agent.
3. Select **Send to Agent**. A busy Agent shows **Add to queue**; an offline Agent shows **Queue for Agent**.
4. Open the task and follow its progress. The owner should also watch the Runner terminal.
5. When it completes, inspect **Code changes**, **Test output**, the result, and the recorded commit SHA.

The Runner clones/fetches the project, asks Codex to implement the request, executes the configured test command, commits, and pushes to the shared working branch. It does not automatically open a pull request or merge into the base branch. A request that changes no files may still produce an empty audit commit.

### Where approvals happen

Implementation approvals are handled in the **Agent owner's Runner terminal**, not in the requester’s browser or a separate chat with Codex. The task can display **Waiting for owner** while the terminal shows a command or file diff and asks:

```text
Approve once? [y/N]
```

The owner inspects the request and answers there. Depending on local Codex policy, even a read-only shell command can require approval. Keeping a Runner in a background process without usable standard input can leave these requests unanswered.

The verified-goal review described below uses a separate read-only session and refuses write-permission escalation. It does not ask the owner to authorize the reviewer to edit the solution.

## 8. Run a verified goal

After your first direct task proves that the local setup works, use **Verified goal** for behavior with explicit acceptance conditions.

For a project that already has a settings form, an example is:

| Input | Example |
| --- | --- |
| Goal | Preserve a user's settings draft when validation fails |
| Context | The existing settings form clears entered fields after an invalid submission. Keep its current validation rules and API behavior. |
| Acceptance criteria | An invalid submission preserves entered values; the validation error is visible; the user can correct the input and successfully resubmit; existing regression tests continue to pass |
| Maximum iterations | `2` |

Enter each acceptance criterion on a separate line. Adapt the example to code and behavior that actually exist in your project. The UI accepts 1–12 distinct criteria, up to 500 characters each; context is limited to 10,000 characters and the goal/request to 20,000. The iteration budget is 1–3.

Select an Agent using a current source-built Runner and submit the goal. Each round consists of implementation, actual project tests, and a fresh read-only Codex review of every criterion. Fixable review findings can trigger another implementation round within the agreed budget. Choosing one iteration allows one round, not one failure followed by an extra free retry.

The review is a new Codex thread on the same Runner and account. It is independent of the implementation thread's conversation, but it is not a different team member or necessarily a different model.

Publication requires passing tests, explicit passing evidence for every agreed criterion, no remaining review issues, and a match between the reviewed Git tree and the code being committed. Missing or duplicated checks, unknown evidence, malformed review output, or changes during/after review prevent publication. This provides a checkable gate, not a guarantee that an AI review will discover every defect.

### Inspect successful delivery

Open the task's **Overview**, **Code changes**, **Test output**, and **Activity**. Check the acceptance history as well as the final result. Use **Export** to preview the report, then **Copy Markdown** or **Download Markdown** to retain the existing evidence.

From a separate checkout of your project, you can verify the recorded commit without modifying the Runner's managed clone:

```sh
git fetch origin
git log -1 origin/codex/team-agent-runtime
git show COMMIT_SHA
```

Replace the branch and `COMMIT_SHA` with the actual values. Another completed task may have advanced the branch, so an older task's SHA need not remain at the tip. Review and merge through your team's normal Git workflow.

## 9. Handle blocked work and interruptions

| Situation | What the current version does | Next action |
| --- | --- | --- |
| Selected Agent is offline or paused before execution | The task waits; other runnable tasks can proceed | Wait for its owner, or use **Reassign** and **Update assignment** on a queued/waiting task |
| Owner approval is pending | The active task retains the project execution slot | The owner answers in the Runner terminal |
| Tests, Codex, review, or push fails | The task needs attention; the Agent is paused and local work is preserved | Read the error and evidence, fix the underlying problem, then requeue and have the owner resume sharing |
| Runner or Coordinator disconnects during an active task | The original assignment and project lock are retained | Restart with the same data directories; reconnect the original Runner |
| Verified task reaches its iteration limit | The attempt stops without a passing completion | Inspect the review; retry only after addressing the cause, or create a new goal with a revised agreement |

### Retry, reconnect, and feedback are different operations

**Reconnect** resumes the same execution and budget. A verified goal's original baseline, settings, workflow sequence, and review history are persisted. Recovery cannot treat an old task commit as proof that acceptance passed: the Runner revalidates tests and review before completing a preserved accepted result.

**Requeue task** starts a new attempt with the same goal, criteria, and iteration limit. Previous verified-run evidence is archived in the task's activity. The Agent owner must use **Resume sharing** after resolving the local issue; simply requeueing does not unpause that Agent. An eligible queued/waiting retry can instead be reassigned.

**Save note** records feedback but does not restart work or alter an already assigned goal. **Create follow-up goal** carries the earlier result and feedback into an editable new draft. Review its scope, acceptance criteria, and budget before submitting; it does not inherit a previous passing verdict.

### Preserve the managed clone when recovery asks for inspection

The Runner's error identifies the managed repository path and its project key. Stop the Runner before manually repairing that clone, save a backup of the entire Runner directory, and inspect the files, Git status, and remote branch. Do not force-push, reset, or delete the clone as a routine reconnect step: it may hold the only copy of unfinished edits or a commit whose push failed.

If you have deliberately decided to discard that managed workspace's local edits and unpublished commits, the explicit reset command is:

```sh
node apps/runner/dist/cli.js runner --coordinator 'https://team.example.com' --name 'Alex Codex' --reset-managed 'PROJECT_KEY'
```

Use the key reported by the Runner, add your original `--data-dir` if customized, and run this only after the Runner has stopped and you have preserved needed work. This command performs a destructive reset/clean, then exits; restart normally afterward. It does not itself change the web task's status or resume a paused Agent. Avoid `--reset-managed all` unless every managed project is intentionally being discarded.

An administrator can use **Emergency release** only for an active task whose Agent is offline, after confirming that the original Runner has actually stopped. It moves the task to needs-attention and frees the project execution slot. A network outage alone is not evidence that a Runner has stopped editing or pushing.

## Network deployment

### A trusted LAN or private network

On the Coordinator host, change `.env` to use a reachable address, for example:

```dotenv
TEAM_AGENT_HOST=0.0.0.0
TEAM_AGENT_PORT=4310
TEAM_AGENT_PUBLIC_URL=http://192.168.1.20:4310
TEAM_AGENT_DATA_DIR=/absolute/persistent/path/coordinator
TEAM_AGENT_DEMO_MODE=0
```

On Windows, use an appropriate absolute data path such as `C:/TeamAgentData/coordinator`. Restart with the same `node --env-file=.env ...` command. Allow the Coordinator port through the host firewall only for the intended team network, then verify `/api/health` from another member's computer. Replace the example IP with a stable address or hostname you control.

HTTP does not encrypt invitation tokens, cookies, or project data. Use it only for local evaluation or a network whose protection your team has explicitly chosen; use HTTPS for a shared deployment.

### HTTPS behind a reverse proxy

Use a dedicated hostname such as `team.example.com`, with the app at the hostname's root. Arbitrary URL subpath hosting is not configured by this guide. Bind a source Coordinator to loopback when the proxy is on the same host, and set:

```dotenv
TEAM_AGENT_HOST=127.0.0.1
TEAM_AGENT_PORT=4310
TEAM_AGENT_PUBLIC_URL=https://team.example.com
TEAM_AGENT_DATA_DIR=/absolute/persistent/path/coordinator
TEAM_AGENT_DEMO_MODE=0
```

The proxy must forward HTTP requests, the Runner's WebSocket connection at `/api/runner`, and long-lived server-sent events at `/api/stream`. Avoid buffering the event stream and configure timeouts for long-running connections. All Runner owners must be able to reach the same HTTPS URL and trust its certificate. The Runner connects outward; you do not need to open an inbound port on every owner's computer.

For example, on a host with Caddy already installed and a hostname/certificate setup that meets its requirements, the Caddyfile can contain:

```caddyfile
team.example.com {
    reverse_proxy 127.0.0.1:4310
}
```

Caddy supports WebSocket proxying and streaming responses; its [reverse-proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) and [automatic HTTPS requirements](https://caddyserver.com/docs/automatic-https) describe the deployment details. Team Agent does not provision DNS, certificates, a proxy, or a VPN for you.

Restrict network access to your intended users and devices. If an additional access gateway sits in front of the app, verify that it also permits the native Runner WebSocket; an HTML browser-login redirect will not authenticate a Runner. `TEAM_AGENT_PUBLIC_URL` controls generated links and whether session cookies are marked Secure; it does not configure TLS or the listening interface.

<a id="docker-source-build"></a>

### Docker: build this version from source

The base `compose.yaml` pulls the older release image. To run the current workbench, use both Compose files explicitly:

```sh
docker compose -f compose.yaml -f compose.dev.yaml up -d --build
docker compose -f compose.yaml -f compose.dev.yaml logs --tail=100 coordinator
```

Create/edit `.env` first and set the final `TEAM_AGENT_PUBLIC_URL`. Compose reads `.env` for its substitutions. The override builds a local `team-agent:dev` image from your checkout. Read the administrator invite from the container logs and open it at the final team URL.

The container listens on port 4310 internally. The Compose `TEAM_AGENT_PORT` substitution controls the published host port; it does not change the internal port. Compose publishes on host interfaces by default. When a same-host proxy should be the only entry point, this `.env` value limits the published binding to loopback:

```dotenv
TEAM_AGENT_PORT=127.0.0.1:4310
TEAM_AGENT_PUBLIC_URL=https://team.example.com
```

That `IP:port` syntax is specific to Compose's port mapping. A source Node process requires `TEAM_AGENT_PORT=4310` as a number. The Compose service sets `TEAM_AGENT_HOST=0.0.0.0` and `TEAM_AGENT_DATA_DIR=/data` inside the container; the named `team-agent-data` volume persists `/data`.

The Docker image contains the Coordinator, not an owner's Codex Runner. Continue to run and pair current source-built Runners on their owners' machines. A plain `docker compose up -d`, a `:latest` image, or a v0.2.0 Runner installer should not be treated as an upgrade to this source version.

## Persistence, backups, upgrades, and rollback

### What to retain

| Location | Contents | Why it matters |
| --- | --- | --- |
| Coordinator `TEAM_AGENT_DATA_DIR` | SQLite members/sessions, invitations, settings, tasks, messages, assignments, workflow evidence, and server secret | Restores the team's state and identity mappings |
| Runner `--data-dir` or default directory | `runner.json`, device credentials, checkpoints, completion receipts, and `projects/` managed clones | Preserves identity and unfinished/unpublished code |
| Owner's Codex and Git authentication | Managed separately by those tools | Needed again when moving or restoring a Runner |
| Git remote | Published shared-branch commits | Retains published code, but not unfinished local edits or all task evidence |

Store these backups privately: Runner state includes a usable device token, and task history can include private source code. A Markdown task export is useful for review, but is not a replacement for a database and Runner backup.

### Make a consistent backup

Let the active task finish when possible, pause sharing, stop the Runners, and stop the Coordinator before copying its state. SQLite uses WAL mode; copy the entire Coordinator directory, including any WAL/SHM files, rather than copying only a live `.sqlite` file. Copy each stopped Runner's entire data directory as well.

For a source deployment, use your normal filesystem backup after stopping the processes. Keep a separate dated copy instead of overwriting the previous backup. For a source-built Docker deployment, an example is:

```sh
docker compose -f compose.yaml -f compose.dev.yaml stop coordinator
mkdir coordinator-backup-YYYY-MM-DD
docker compose -f compose.yaml -f compose.dev.yaml cp coordinator:/data/. ./coordinator-backup-YYYY-MM-DD/
docker compose -f compose.yaml -f compose.dev.yaml start coordinator
```

Replace the date and choose a new destination. Retain the `.env` deployment settings privately and record the source commit SHA used for the backup. Do not run `docker compose down -v`: it deletes the named data volume.

### Upgrade from source

After stopping active work and taking backups, update a clean Team Agent source checkout:

```sh
git status --short
git pull --ff-only origin main
pnpm install --frozen-lockfile
pnpm build
```

Handle any local source changes before the pull; do not discard them to force an upgrade. Restart the Coordinator with the same `.env` and data directory, then restart every Runner from its updated checkout with its original data directory and without `--pair`. Run doctor, check that Agents appear, and try one bounded task.

For Docker, update the source checkout and rerun `docker compose -f compose.yaml -f compose.dev.yaml up -d --build` while retaining the same Compose project and named volume. Runners are still upgraded separately from source.

The database creates/migrates its schema at startup. There is no automatic downgrade migration or managed updater. To roll back, stop all processes, restore the matching pre-upgrade Coordinator/Runner backups and source revision together, preserve any newer work separately, and verify the remote Git branch before resuming. Restore container data into a stopped, clean destination with ownership writable by its `node` user. Do not start old and new Coordinators against the same database or duplicate a Runner identity across live processes.

## Troubleshooting

| Symptom | Check and remedy |
| --- | --- |
| You see prefilled demo tasks and simulated evidence | You opened GitHub Pages, `demo:browser`, or a Coordinator with `TEAM_AGENT_DEMO_MODE=1`. Open your own non-demo Coordinator and complete its invitation flow. |
| Browser says web assets have not been built | Run `pnpm build` from the source checkout; restart the built Coordinator. `pnpm coordinator` alone starts the backend. |
| `.env` changes seem ignored | Use `node --env-file=.env apps/coordinator/dist/server/index.js` for the source process, or the explicit Compose files for Docker. Check inherited environment variables and restart the process/container. |
| Invitation is invalid or expired | Use an unclaimed link less than seven days old. On an empty installation, use the newest bootstrap link after a restart; for members, ask the administrator to create a fresh personal invitation. |
| You cannot recover an existing member/admin after clearing cookies | There is no account-recovery UI. Keep any still-valid administrator session, preserve the database, and arrange controlled recovery with the operator; deleting the database is not a login fix. |
| Login works on one address but not another | Use one canonical hostname/protocol. Cookies are browser/origin-specific; an HTTPS-configured deployment also requires HTTPS for Secure session cookies. |
| Pairing fails after 15 minutes or after first use | Generate a new one-time token for initial pairing. Restart an already paired Runner without `--pair` and with its original data directory. |
| `Codex is not signed in`, `spawn codex ENOENT`, or app-server startup fails | Check `codex --version`, `codex login status`, `PATH`/`CODEX_BIN`, and doctor in the exact account/environment used to launch the Runner. Install/update Codex through the official guide above. |
| Doctor passes but a real task times out or reconnects repeatedly | Doctor only checks login/handshake. Inspect the Runner's actual Codex error and the owner's account/network configuration. A connected Coordinator cannot prove the model service is reachable. |
| Task needs attention after a Git authentication or push error | Repeat the Git clone/fetch and dry-run push checks as the Runner owner. Resolve credential-manager/SSH access and shared-branch rules. Preserve the managed clone; an unpublished task commit may already exist there. |
| Tests cannot find dependencies, files, or environment variables | Remember that tests run in the managed clone, not your everyday checkout. Install required runtimes, supply the Runner environment, and use a terminating test command with appropriate dependency setup. |
| A verified goal says tests are not configured | Save a real project test command. Then requeue after addressing the issue and have the owner resume sharing. Empty test output is not acceptance evidence. |
| A verified goal asks for a newer Runner | Build/run the current source on that Agent's computer. An older v0.2.0 release Runner does not advertise `goal-workflow-v1`. |
| Work stays queued although an Agent is visible | Check whether it is paused/busy/offline, whether another task retains the project lock, and whether a verified goal selected an older Runner. |
| Task is waiting for owner | Inspect the original Runner terminal and answer its approval prompt. There is no browser approval button. |
| Managed workspace has local commits/edits, diverged, or changed after review | Stop and inspect the preserved clone. Reconcile deliberately and back it up; do not reset or force-push merely to make the status green. |
| Another Runner already owns the data directory | Stop the duplicate process, or use a different directory for a genuinely separate identity. Do not delete an active process lock to run two instances. |
| Web page loads but events or Agents disconnect behind a proxy | Verify `/api/stream` streaming, `/api/runner` WebSocket upgrades, timeouts, certificate trust, and that an access gateway does not return an HTML login page to the Runner. |
| Port 4310 is already in use | Stop the other service or choose a new numeric source port and matching public URL. For Docker, change the host port mapping. Start only one Coordinator against each database. |
